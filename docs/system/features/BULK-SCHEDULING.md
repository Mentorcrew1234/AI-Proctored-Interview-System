# Bulk interview scheduling

Schedule many interviews from a spreadsheet instead of filling the form once per
candidate.

**This is not a separate kind of interview.** Every record it creates is made by
calling the same `InterviewService.create` the single-schedule form uses, so a
bulk-created interview has the same invite token, the same `SCHEDULED` status,
and runs through the same session → proctoring → AI interview → evaluation →
report pipeline. Nothing downstream knows or cares how it was created.

---

## The flow

```
Download template → fill in → upload → validate → review → CONFIRM → scheduled
                                        ▲                    │
                                   nothing created      the only step
                                        │               that writes
                                   you can walk away here
```

**Uploading does not schedule. Validating does not schedule.** Only pressing
*Confirm & schedule* creates records. Walking away after uploading leaves the
database untouched.

## Permissions

| Role | Access |
|---|---|
| Recruiter | Yes |
| Admin | Yes |
| **Candidate** | **No — 403** |

The signed-in user becomes the recruiter on every interview created, exactly
as with single scheduling. Uses the existing role system; nothing was changed.

## The template

Download it from the Bulk Schedule page. It has an **Interviews** sheet for the
data, two greyed example rows to delete, and an **Instructions** sheet listing
every accepted value.

| Column | Required | Accepted values |
|---|---|---|
| Interview Name | Yes | Your name for the drive, e.g. "Java Developer - Campus Drive 2026". Many rows may share one. |
| Candidate Name | Yes | Any text |
| Candidate Email | Yes | Valid email address |
| Interview Date | Yes | `YYYY-MM-DD`, not in the past |
| Interview Time | Yes | 24-hour `HH:MM` |
| Domain | Yes | **Any topic or stack**, up to 80 characters. A familiar name folds onto its canonical spelling (`java` → `Java`). |
| Experience Type | Yes | `FRESHER` or `EXPERIENCED` |
| Years of Experience | **If EXPERIENCED** | 1–50. Blank or 0 for a fresher. |
| Language | Yes | English |
| Interview Type | Yes | `TECHNICAL` or `HR_GENERAL` |
| Question Count | No | 1–10, defaults to 5 |
| Test Duration (minutes) | No | 1–180, defaults to 30. The clock starts when the candidate begins, not at the scheduled time |
| College Name | No | Any text, up to 150 characters. **Only used when the candidate account has to be created** — an existing account is never altered by an upload. |
| Location | No | Any text, up to 120 characters. Creation only, same as College Name. |
| Skills | No | Comma-separated, up to 255 characters. Each becomes a filter option on the candidates page. Creation only. |

Interview questions are **not** in the template — they are generated by the AI
when the candidate starts.

> **Not in the template, on purpose:** the **question mode** (FIXED or ADAPTIVE).
> Bulk-created interviews inherit the server default, and the choice stays on the
> single scheduling form. Bulk doing *less* than the single form is safe; the
> rule that must never break is bulk doing *more* — see design decision 13 in
> `CLAUDE.md`.

### Tolerances

Recruiters do not need to be precise about formatting:

- Dates also accept `DD-MM-YYYY`, `DD/MM/YYYY`, `YYYY/MM/DD`, `DD-MMM-YYYY`
- Times also accept `H:MM`, `HH:MM:SS`, `2:15 PM`
- Values are case-insensitive: `fresher`, `java`, `technical` all work
- Real Excel date/time cells work as well as text
- Blank rows anywhere in the file are ignored

## Validation

Runs in five levels, all server-side, before anything is created.

**1 — File.** Present, `.xlsx`, under 5 MB, readable, has a usable sheet, and
carries every required header. A missing header names the column:

> Missing required column(s): Candidate Email. Download a fresh template and use
> its header row.

**2 — Row.** Every required field present; email, date and time well-formed;
date not in the past; domain, experience type, language and interview type all
matching supported values; question count in range.

**3 — Conditional.** `EXPERIENCED` must have years of experience. `FRESHER` may
leave it blank or 0 — and either way the stored value is null, never 0, matching
the single-schedule rule.

**4 — Duplicates within the file.** Same candidate email at the same date and
time twice is flagged on the second occurrence; the first is kept.

**5 — Database.** Candidate exists? Is the account a candidate, and enabled? Is
that candidate already scheduled at that exact time? These are the rules the
single form already applies — none were invented for bulk.

Every error names the Excel row, the candidate, the field and the problem:

> Row 14 · Rahul Kumar · **Interview Date**: Interview date and time cannot be in
> the past.

### Partial files are normal

A file with 96 good rows and 4 bad ones is not rejected. You see both counts,
can download an **error report** (`.xlsx`) listing only the bad rows and their
problems, and can schedule the 96. **Invalid rows are never scheduled.**

## Review and confirmation

The review page shows counts, every problem row with its errors, and a full
preview of what would be created — including which candidates will have accounts
created for them. Nothing has been written at this point.

Confirming asks once more, then schedules. The button disables itself on submit,
and the server refuses to schedule the same batch twice regardless — a
double-click, a refresh, or a re-posted form all show the original result rather
than scheduling again.

---

## What happens on confirmation

For each valid row, in its own transaction:

1. The candidate is found by email, or **created** via the existing `UserService`
   with the CANDIDATE role and a generated password.
2. `InterviewService.create` is called — the same method the single form uses.
3. The result gets a UUID invite token and `SCHEDULED` status like any other.

Each row is written independently, so one failure cannot roll back rows that
already succeeded. Anything that fails is listed on the result page with its
Excel row and reason; failures are never hidden.

### Newly created candidate accounts

A generated password is **never persisted** — only its bcrypt hash is — so it can
be read in exactly two places, and both are temporary:

1. **The result page and the downloadable result workbook**, available only while
   the batch is staged (30 minutes).
2. **An "account credentials" email to the candidate**, sent automatically when
   `app.mail.enabled` is true. This is a separate email from the invitation:
   `BulkRowScheduler` publishes `CandidateAccountCreated` for a row that actually
   created an account, and only for such a row — an existing candidate scheduled
   again receives the invitation only. See `docs/system/features/EMAIL-NOTIFICATIONS.md`.

**With mail off (the default), you must send the passwords yourself**, from the
result page, before the batch expires. Sending is best-effort either way: a
failure is logged, never thrown, and never costs the interview.

---

## Result

Counts of scheduled, failed and skipped, the invite link for every interview
created, any new account credentials, and a downloadable `.xlsx` workbook of the
whole batch.

The result workbook is built by `BulkExcelService.buildResultReport` and has one
row per outcome: `Status` (`SCHEDULED` / `FAILED`), Excel row number, interview
name, candidate, email, scheduled time, domain, invite token, whether the account
was created, the generated password, and the failure reason. It is reachable only
while the batch is still staged, because **the plaintext password is never
persisted** — this workbook is the only place it can be read.

## Design notes

**Why the endpoints are not under `/api/**`.** That path is the stateless-JWT
chain used by the candidate's React app. Bulk scheduling is a staff web page on
the session + CSRF chain like every other admin screen; putting it under
`/api/**` would force the page to obtain a bearer token for no benefit.

| Path | Method | Purpose |
|---|---|---|
| `/scheduling/bulk` | GET | Upload page |
| `/scheduling/bulk/template` | GET | Download the blank template |
| `/scheduling/bulk/validate` | POST | Parse and validate. **Creates nothing.** |
| `/scheduling/bulk/errors/{batchId}` | GET | Error report for invalid rows |
| `/scheduling/bulk/confirm` | POST | **The only endpoint that creates interviews** |
| `/scheduling/bulk/result/{batchId}` | GET | Re-display a completed batch |
| `/scheduling/bulk/report/{batchId}` | GET | Result workbook (`.xlsx`) |

**Why the validated batch is held server-side.** The confirm step carries only an
opaque batch id. If the browser posted the rows back, the server would be
trusting the client's idea of what passed validation. Batches are held in memory
for 30 minutes, scoped to the user who uploaded them, and **re-validated from
scratch at confirmation** — time has passed, and a date may now be in the past or
a candidate may have been disabled since the upload.

---

## Limitations

- **In-memory staging.** A restart, or a second application instance, loses
  pending batches; the user re-uploads. Suits a single-instance prototype and is
  not worth a datastore here.
- **Generated passwords are shown once.** No email integration means manual
  distribution. If lost, an admin can create a new account.
- **Synchronous.** 100 rows complete in a few seconds. Thousands would want a
  background job, which this prototype deliberately does not build.
- **`.xlsx` only.** Legacy `.xls` and CSV are rejected with a clear message.
- **Clash detection is exact-time.** Two interviews for the same candidate one
  minute apart are allowed; the existing system has no interview-duration
  concept to overlap against.
